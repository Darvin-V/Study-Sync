# StudySync AI — Known Limitations & Deployment Constraints

To maintain transparency, this document details the current technical boundaries, architectural trade-offs, and deployment constraints of StudySync AI.

---

## 1. Hosting & Free-Tier Infrastructure Constraints

### 1.1 Service Sleep & Cold Start (Render / Fly.io Free Tiers)
- **Constraint**: On zero-cost hosting tiers (e.g., Render Free Web Service), container instances automatically spin down after 15 minutes of inactivity.
- **Observed Behavior**: The first incoming HTTP request to a sleeping container experiences a 40–60 second cold-start delay while the container boots and Litestream checks Backblaze B2 snapshot health.
- **Mitigation**: A health-check warming cron (e.g., pinging `/health` every 10 minutes) can reduce sleep frequency, but production institutional deployments require a paid instance (~$7/month).

### 1.2 Ephemeral Disk & Litestream Replication Lag
- **Constraint**: Cloud free tiers offer ephemeral filesystems that discard local disk files upon container restarts.
- **Implementation**: StudySync AI integrates `litestream` to replicate SQLite WAL frames to Backblaze B2 object storage.
- **Limitation**: If an unexpected container termination occurs during an active transaction before a WAL frame flush (typically $< 1$ second window), the un-flushed transaction may be lost upon subsequent container restoration.

### 1.3 Outbound Email Quotas (Email OTP)
- **Constraint**: Free tiers for transactional email services impose rate limits:
  - Resend: 3,000 emails/month (100 emails/day).
  - SendGrid: 100 emails/day.
- **Risk**: A sudden influx of registrations exceeding 100/day will exhaust the quota, causing OTP dispatches to fail with HTTP 500 or provider rejection.

## 2. Real-Time Collaboration & Audio/Video Boundaries

### 2.1 Transport Mechanism (HTTP Polling vs. WebSockets)
- **Constraint**: Topic room messages, active participant rosters, and doubt status updates currently utilize client-side HTTP polling (1–3 second intervals) and manual refreshes.
- **Impact**: Live updates are not sub-millisecond. High user density in a single room generates frequent polling requests. Bi-directional WebSockets (`ws://`) are scheduled for Phase 16.

### 2.2 Audio/Video Meetings & External Conferencing
- **Constraint**: Native browser-to-browser WebRTC audio/video calls require dedicated STUN/TURN relay infrastructure to reliably traverse symmetric corporate/university NAT firewalls. Free public STUN servers frequently fail on campus Wi-Fi.
- **Current Architecture**: The application supports integrated virtual study call lifecycles and external conferencing links (Google Meet, Zoom, Microsoft Teams) with server-side URL validation. Direct native WebRTC media streaming is not yet bundled.

---

## 3. Machine Learning & Recommendation Boundaries

### 3.1 Experimental ML Status (No Trained Model in Production)
- **Status**: The machine learning model evaluated in Phase 6 (L2-Regularized Logistic Regression) is **strictly experimental** and resides in `scratch/ml_experiment.js`.
- **Reason**: The live SQLite database contains only 8 recommendation records, all in status `presented` (zero label variance). Training on live data was halted to avoid ill-conditioned learning or fabricated accuracy claims.
- **Production Logic**: All user recommendations are generated by deterministic, transparent heuristic algorithms.

### 3.2 Feedback Loop Risk (Filter Bubble)
- **Constraint**: If recommendations prioritize high historical completion rates, popular topics will dominate, potentially neglecting challenging foundational areas.
- **Mitigation**: The heuristic algorithm explicitly boosts weak topics ($< 70\%$ quiz scores) by $+30$ points, ensuring academic deficiencies remain visible.

---

## 4. Platform & Browser Permissions

### 4.1 Do Not Disturb (DND) Automation
- **Constraint**: Standard web security sandboxes prevent browser JavaScript and PWAs from modifying operating system DND or focus mode settings.
- **Behavior**: StudySync's Distraction Shield silences internal application toasts and alerts, while providing an on-screen prompt instructing the user to enable their device's native DND switch.

### 4.2 Local Database Concurrency
- **Constraint**: SQLite operates with a single writer lock. While Write-Ahead Logging (`WAL`) allows unlimited concurrent readers, extreme burst writes ($> 1,000$ concurrent writes/second) may trigger `SQLITE_BUSY`.
- **Mitigation**: `PRAGMA busy_timeout = 5000;` is configured. Large-scale institutional deployments ($> 10,000$ active concurrent students) will require a PostgreSQL backend.
